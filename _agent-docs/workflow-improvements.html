Tier 3: Small — Deduplicate Repeated Patterns

Extract shared logic into reusable functions. Reduces maintenance burden and bug surface.

Small
Extract data-source file lookup into a function

The pattern of splitting data_source by _ and dispatching to the correct file list appears in 01_01. The source-specific scripts (01_02b, 01_02c, 01_02d) no longer need this since each handles one source exclusively. 

get_data_files <- function(data_source, file_lists) {
  parts <- strsplit(data_source, "_")[[1]]
  Reduce(union, lapply(parts, function(p) file_lists[[p]]))
}

parse_years_to_remove <- function(year_str) {
  parts <- strsplit(year_str, ",")[[1]]
  unlist(lapply(parts, function(part) {
    if (grepl(":", part)) {
      bounds <- as.integer(strsplit(part, ":")[[1]])
      seq(bounds[1], bounds[2])
    } else {
      as.integer(part)
    }
  }))
}

Tier 6: Architectural — Pipeline Orchestration

Transforms the project from a collection of scripts into a reproducible, cacheable pipeline.

Architectural
Adopt targets for pipeline orchestration

The current workflow is a sequence of R scripts that must be run manually in order. There is no dependency tracking, no caching, and no way to know if outputs are stale. A targets pipeline would:

  • Automatically detect which steps need re-running when inputs change
  • Cache intermediate results (critical for steps that take hours/days)
  • Make the full dependency graph explicit and inspectable
  • Enable parallel execution of independent branches (e.g., 02_01a and 02_01b)

Suggested structure: 

# _targets.R
list(
  tar_target(site_info, read_csv("data/site_info.csv")),
  tar_target(raw_data, load_raw_data(site_info)),
  tar_target(soil_temp, estimate_missing_soil_temp(raw_data)),
  tar_target(nec_qc, quality_control_nightly_nee(soil_temp, site_info)),
  tar_target(acclimation_temp, fit_er_curves(nec_qc$temp, model = "temperature_only")),
  tar_target(acclimation_water, fit_er_curves(nec_qc$water_gpp, model = "temperature_water_gpp")),
  tar_target(acclimation_decomposed, decompose_acclimation(acclimation_temp, acclimation_water)),
  # ... etc
)
Project-wide
Adopt renv for dependency management

Currently there is no record of which package versions were used. renv::snapshot() creates a lockfile that ensures reproducibility. Combined with targets, this makes the full analysis reproducible from a clean install.

Project-wide
Replace librarian::shelf() with library() + renv

librarian silently installs missing packages, which masks environment problems. With renv managing the package library, library() is sufficient and failures are informative.

All scripts
Create a shared utility R package or module

After extracting duplicated patterns (Tier 3), place shared functions in a local package (e.g., R/utils.R sourced at the top, or a minimal {thermal.acclimation} package). This avoids copy-pasting utility functions across scripts and makes them independently testable.

Project-wide
Add a Makefile or targets-driven CLI entry point

Provide a single command to run the full pipeline: make all or targets::tar_make(). Individual steps should also be runnable in isolation for development.

Parallelization Across Sites

A natural question when considering a targets refactor (Tier 6) is whether individual steps can run in parallel across sites. The answer varies by script.

Per-Site Parallelization Map

Script Parallelizable? Cross-Site Dependency Caveats
01_01 Yes None Trivial; each site trains its own RF on its own data
01_02c Yes None Trivial gather of feature_gs at end (one row per site)
01_02d Yes None Trivial gather of feature_gs at end (one row per site)
01_02b Yes US-BZS reads US-BZF raw data Input-level dependency (raw file), not output-level — no task ordering; hoist amf_site_info() API call out of loop
02_01a/b Partially Pooled brm fit per time window See details below
03_01 Yes None (trivial join at end) Per-site summary computation; final assembly is just a left-join
03_02 No RF trained on combined multi-site dataset Fundamentally non-parallelizable; learns cross-site relationships
04_02 Yes None Per-site brm with generic priors; most expensive step (~7 hrs) and biggest speedup target

The 02_01a/b Bottleneck

These scripts loop over sites but first fit a pooled brm model on all sites' data in each 14-day time window before site-specific year-level fits can run. The pooled fit initializes priors: 

# 02_01a, line 165 — data from ALL sites in this window
data <- a_measure_night_complete %>% filter(between(DOY, window_start, window_end))
mod0 <- brms::brm(brms::bf(frmu, param, nl = TRUE), data = data, ...)

# mod0 posteriors become the priors for per-site fits
priors$prior[priors$nlpar == 'alpha'] <- paste0("normal(", brms::fixef(mod0)["alpha_Intercept", "Estimate"], ", 1.0)")

Recommended refactor: Split into two phases:

  1. Phase 1 (sequential): Run the pooled brm fit for each time window once. This is fast relative to the per-site fits because it only runs once per window.
  2. Phase 2 (parallel): With priors established, run all site×year fits in parallel — these are fully independent once priors are available.

Alternatively, use generic priors (e.g., normal(0, 1)) instead of data-derived priors. The per-site fits will converge anyway given enough MCMC iterations; the pooled fit just speeds convergence slightly.

The 03_02 Non-Parallelizable Step

The Random Forest in 03_02 is trained on the combined multi-site dataset (~117 sites, one row each) to learn cross-site predictor–response relationships. This cannot be split per-site. However, it runs in ~10 minutes (fast), so parallelization is unnecessary here.

Recommended Parallelization Strategy

If using targets, the pipeline graph naturally exposes parallelism. Within each step, parallelize the site loop with future.apply::future_lapply() or furrr::future_map(): 

# Example: parallelize 04_02 (biggest speedup: ~7hrs → ~20min on 20 cores)
library(future.apply)
plan(multisession, workers = 20)

results <- future_lapply(seq_along(site_ids), function(i) {
  # ... existing per-site brm fitting logic ...
})

Key prerequisite: Hoist the amf_site_info() API call in 01_02b out of the site loop before parallelizing, to avoid N identical network calls and potential rate-limit issues.
